# 01 · 脚本接口约定

> 本文件是硬约束。任何一条不满足，脚本都会被引擎拒绝加载或在检查中失败。

## 一、你要交两个文件

| 产出 | 路径 | 内容 |
|---|---|---|
| 对战脚本 | `agents/agent-<你的 id>.js` | 零依赖 ES Module，导出 `meta` / `deck` / `spirit` / `color` / `choose` |
| 设计说明 | `agent-progress/<你的 id>.md` | 中文，六节：模型与策略名 / **组卡思路** / **对战思路** / 模式适配 / 动作优先级 / 取舍与弱点 |

`<你的 id>` 见 `04-任务说明.md` 的分工表，一字不差。

## 二、脚本必须导出五个东西

```js
export const meta = {
  id: 'hy4',                       // 你的短 id，与文件名一致
  model: 'hy4',                    // 显示名，照抄分工表「显示名」列
  modelId: 'hy4std',               // 模型 ID，照抄分工表「模型 ID」列
  name: '策略名称',                 // 你自己起
  desc: '一句话说明为什么选这套打法',
  primaryMode: 'standard',         // 你的主责模式，见 04-任务说明.md
  modes: ['standard', 'blitz', 'grand', 'duo'],  // 必须写全这四项
};

export const deck = { /* 卡名: 张数 */ };   // 或 ['卡名','卡名', ...] 的数组
export const spirit = '圣所守夜人';          // 从 8 个灵体里选 1 个
export const color = '白';                   // 你的主色，用于灵能池显示

export function choose(view, moves) {
  // 从 moves 里挑一个原样返回
  return moves.find((m) => m.type === 'pass') || moves[0];
}
```

**`choose` 的返回值必须是 `moves` 数组里的一个元素，原样返回，不得新建对象、不得改字段。**
引擎会把返回值与真实动作逐字段比对，改过就判为非法动作并强制让过。

## 三、`choose` 什么时候被调用

只要轮到「你」做决定，引擎就调用一次。你可能处在这几种情形，用 `view` 判断：

| 情形 | 判据 | `moves` 里会有什么 |
|---|---|---|
| 灵体检视 | `view.inspect` 非空 | `inspectTake`、可能 `inspectReveal` |
| 自己的攻击阶段 | `view.combat.stage === 'attackers'` | 每个可攻击单位 × 每个目标，加 `pass` |
| 自己的支援阶段 | `view.combat.stage === 'support'` | `supportSpirit`、`pass` |
| 对方攻击、你要阻挡 | `view.combat.stage === 'blockers'` | 每个可阻挡单位 `block`，加 `pass` |
| 确定阻挡顺序 | `view.combat.stage === 'order'` | 若干 `orderBlockers`（带 `order` 数组） |
| 自己的主要阶段 | `view.phase` 为 `main1`/`main2` 且 `view.active === view.me.idx` 且 `view.chain` 为空 | `play`、`setEssence`、`ability`、`spiritSpecial`、`spiritDraw`、`tapEssence`、`pass` |
| 响应对方的卡 | `view.priority === view.me.idx` 但 `view.active !== view.me.idx`，或连锁非空 | 只有 `play`（灵感卡）与 `pass` |
| 其他（start/setup/damage） | 看 `view.phase` | 只有 `pass` |

`view.priority` 是「现在轮到谁决定」，`view.active` 是「这一回合是谁的」。两者不同就说明你在响应别人。

## 四、`view` 有哪些字段

```js
{
  seed, turn, active, priority, phase,
  mode,                       // 'standard' | 'blitz' | 'grand' | 'duo'
  modeSpec: { name, life, handStart },
  me: {                       // 你自己，手牌可见
    idx, name, color, spiritName,
    spirit: { tapped, crit, dream },   // crit 是暴击指示物，dream 是梦境指示物
    life,                     // 生命卡组剩余张数 = 当前生命值
    deck, handCount,
    hand: [Card],             // 只有自己的手牌可见
    essence: [Card], field: [Card], grave: [Card], armor: [Card],
    exileCount, mana,         // mana 例：{ 白: 2, 灰: 0, ... } 已产未花的灵能
    stats, usedDimension, turnCount,
  },
  opp: { ...同上但 hand 为 undefined，只有 handCount },
  chain: [{ name, controller, countered, event }],
  combat: { stage, attackerUid, target, blockers } | null,
  inspect: { uid, card } | { hidden: true } | null,
  over, winner,
}
```

`Card` 对象的字段：

```js
{
  uid, id, name, type, color,        // type: 灵像 / 灵感 / 灵性
  cost: { total, colored, grey, colors? },
  attack, impact, vitality,          // 卡面原始值
  atk, imp, hp,                      // 实时值，含持续加成与伤害折算；战场上的卡必须以这个为准
  keywords: [], text, trigger,       // trigger: LT / MT / CT / ST / —
  zone, damage, tapped,
  token,      // 是否衍生物
  doomed, substitute,
}
```

**只有 `me.hand` 看得到具体卡，`opp.hand` 是 undefined。** 不要试图从对手手牌或牌库顺序推信息。

## 五、`moves` 里每种动作的字段

| `type` | 其他字段 | 含义 |
|---|---|---|
| `play` | `uid`、`mode`、`targets[]` | 使用手牌。`mode` 是变体：`main` 普通、`bury` 葬送、`condense` 凝聚、`destroy2` 破坏 2、`both`、`sacrifice` 献祭、`extract` 提取灵感、`tokens`/`damage`/`charge` 梦境战将三选一 |
| `setEssence` | `uid` | 把手牌设为灵质（每回合 1 次） |
| `tapEssence` | `uid` | 横置一张灵质产 1 点灵能；通常不必要，费用支付会自动横置 |
| `ability` | `uid`、`mode?`、`targets[]` | 启动场上单位或灵质的启动式能力 |
| `spiritSpecial` | `name`、`targets[]` | 灵体专属启动能力 |
| `spiritDraw` | — | 横置灵体，检视主卡组顶 1 张（随后进入 `inspect`） |
| `attack` | `uid`、`target`（单位 uid 或字符串 `'spirit'`） | 宣告攻击。`'spirit'` 表示打对方生命卡组 |
| `block` | `uid` | 用该单位阻挡当前攻击者 |
| `orderBlockers` | `order[]` | 确定多个阻挡者的伤害分配顺序 |
| `supportSpirit` | — | 消耗 1 个暴击指示物，给本次攻击 +1000 攻击 / +1 冲击 |
| `inspectTake` | — | 检视后不支付，加入手牌 |
| `inspectReveal` | — | 支付 1 点同色灵能，揭示并加入手牌 |
| `pass` | — | 让过 |

`targets` 是引擎已枚举好的合法目标组合，**不要自己拼 targets**，只能整组接受或跳过这个动作。

## 五之二、`block` 是切换式动作（最容易踩的坑）

`block` 不是「追加阻挡」，而是 **toggle**：

- 该 `uid` **不在** `view.combat.blockers` 里 → 返回它会「宣告阻挡」；
- 该 `uid` **已在** `view.combat.blockers` 里 → 返回同一个它会「取消阻挡」。

所以「每次都挑最优阻挡者并返回 block」会在一对状态之间无限来回：宣告 → 取消 → 宣告。

**必须从候选里 filter 掉已宣告的单位，不能只给它扣分。** 扣分不够，是因为「让过」在某些局面下也会被扣到很低（例如对方打脸且冲击不小于你的生命张数，你可能给 pass 一个很重的惩罚）。一旦 pass 的分数低于那个「本该被排除的 block」，`pickBest` 就会选中它，循环就出现了。

```js
if (view.combat.stage === 'blockers') {
  const chosen = view.combat.blockers || [];      // 已宣告的阻挡者 uid
  const fresh = moves.filter((m) => m.type !== 'block' || !chosen.includes(m.uid));
  return pickBest(fresh, score) || moves.find((m) => m.type === 'pass');
}
```

`order` 阶段同理：每轮都必须返回 `orderBlockers`，不要返回 `pass`。

## 六、硬性约束

1. **零依赖**：不得出现 `import` / `require` / `fetch` / `process`。
2. **无副作用**：不得修改 `view`、`moves` 或其中任何对象；不得对 `moves` 做 `sort()`（要先 `[...moves]` 复制）。
3. **无模块级可变状态**：不要用 `let x` 在模块顶层累计跨回合数据。同一份脚本会被反复加载跑几十局，状态会串局，导致不可复现。需要跨回合记忆就只依赖 `view` 里的公开信息。
4. **必须总能返回**：任何分支都要有兜底，最后一行应是 `return moves.find(m => m.type === 'pass') || moves[moves.length - 1];`。
5. **不得抛异常**：允许在 `choose` 内部用 `try/catch` 包裹自己的评分逻辑，异常时退回让过。外层异常会被引擎记为「脚本异常」并强制让过。
6. **单次决策 < 50ms**：纯打分即可，不要搜索整棵博弈树。
7. **卡组合法**：40—60 张（`grand` 模式 50—60），同名不超过 4，不得投入灵体；**与所选灵体同色的卡牌须 ≥60%**（混色卡按主色计，灰卡只有配灰灵体时计入）。`validateDeck` 会按 `spirit` 的颜色校验这一条。

## 七、关键词含义

| 关键词 | 含义 |
|---|---|
| **质密** | 在灵质区时，可横置发动其启动能力 |
| **启动** | 该卡有横置发动的启动能力 |
| **序曲** | 从手牌使用并进入战场时触发 |
| **终曲** | 该卡离开战场时触发 |
| **回响** | 持续效果，满足条件即生效，通常每回合 1 次 |
| **葬送** | 使用该卡时可选择额外代价换取更强效果 |
| **守护** | 可阻挡已横置的攻击者；被攻击时不必横置即可阻挡 |
| **敏捷** | 可阻挡敏捷攻击者；自身攻击时对方只能用敏捷或守护单位阻挡 |
| **先攻** | 战斗中先结算伤害；若先攻方打死对方，对方不反击 |
| **践踏** | 击杀阻挡者后，剩余伤害分配给对方场上其他单位（不打生命） |
| **超冲击** | 被阻挡时仍可把冲击打向对方生命 |
| **威慑** | 该单位不能被攻击宣言指定 |
| **诱饵** | 对方攻击时，必须优先指定此单位 |
| **灵气** | 不能被对手的效果指定 |
| **自愈** | 自己的结束步骤回复全部伤害 |
| **预制** | 入场当回合即可攻击（不受召唤失调限制） |
| **碾压** | 对生命造成伤害时，超出部分转为额外伤害 |
| **富集** | 横置产灵能时额外产生 |
| **提取灵感** | 该卡可作为「提取灵感」使用 |

## 八、卡组与灵体

- `deck` 用「卡名 → 张数」或卡名数组，两种都收。
- 卡名必须与 `03-卡池.md` 完全一致（含标点）。写错会被校验器点名。
- `spirit` 从 8 个灵体里选 1 个。灵体不进主卡组、不占 40 张额度。
- `color` 是你的主色，只影响界面显示与初始灵能池键名，不影响规则判定；实际能不能付费用看卡面颜色需求。

```bash

node tools/agent-check.mjs <你的 id>
```
